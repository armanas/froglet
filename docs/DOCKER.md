# Docker

Froglet builds and tags these image targets:

- `provider` — provider-mode froglet-node (includes `python3`)
- `runtime` — runtime-mode froglet-node
- `dual` — both provider and runtime in one container
- `froglet-mcp` — MCP server image built and tagged in GHCR

## No-Clone User Stack

Normal users should start with the copyable immutable-release download,
digest-verification, `plan`, and approved `execute` block in the
[Quickstart](https://froglet.dev/learn/quickstart/). Do not fetch an executable
bootstrap from a mutable branch.

The plan is non-mutating and binds the bootstrap and exact platform asset before
the execution call can write Compose or native-service state. Execution then
re-resolves the plan and verifies its
[`froglet.release-bundle.v1`](PUBLICATION_CONTRACT.md#release-bundle-v1), and
installs the immutable-release-bound native binary when the host supports it
(`gh` adds optional workflow-attestation verification). If the native
service manager is unavailable and Docker is selected, it writes
`~/.froglet/agent/compose.yaml` using the bundle's immutable `image_dual`
reference and requires the same local MCP proof before succeeding. MCP config
is generated by the same bootstrap and uses the bundle's pinned `image_mcp`
reference. Neither path clones the repo or resolves a mutable image tag.

The bootstrap stages a small read-only JSON array (or the caller's
`FROGLET_BOOTSTRAP_DATA_FIXTURE=/absolute/path/data.json`), writes a v4
`builtin` + `builtin` data manifest, requires publication-time fixture
verification and a signed Publication Revision, then invokes a row through the
runtime deal path. The caller-supplied JSON form must be a non-empty array of
objects; it is copied into the installation proof directory before
publication. Successful output records the exact release, persistent state
path, service id, publication evidence, and invocation in
`~/.froglet/agent/data-local-proof.json`.

Neither quick-install lane persists bundled demo offers. The lifecycle proof
checks health and the native MCP status path without publishing a service. The
bootstrap's read-only data proof is published and invoked locally, then
confirmed-unpublished; handoff requires the active-offer feed to return to its
captured pre-proof baseline. This keeps built-in offers intact while proving
the temporary service leaves no active publication residue before any later
approved public reachability grant.

The native lifecycle command is `~/.froglet/agent/froglet-service.sh`:

```bash
~/.froglet/agent/froglet-service.sh status
~/.froglet/agent/froglet-service.sh restart
~/.froglet/agent/froglet-service.sh upgrade v0.4.1
~/.froglet/agent/froglet-service.sh rollback
~/.froglet/agent/froglet-service.sh uninstall
```

Upgrade activation replaces a versioned symlink atomically, preserves the data
directory and identity, and rolls back when health or local proof fails.
Uninstall preserves persistent state unless `--purge-data` is explicit.

## Source-Checkout Development Stack

```bash
docker compose up --build
```

That starts:

- provider on `127.0.0.1:8080`
- runtime on `127.0.0.1:8081`

Host token paths used by the generated host-side agent configs:

- `./data/runtime/froglet-control.token`
- `./data/runtime/auth.token`

The default Compose file does not make the provider control token host-readable.
Set `FROGLET_HOST_READABLE_CONTROL_TOKEN=true` whenever a host-side agent or
MCP client needs direct access to `./data/runtime/froglet-control.token`. Those
same generated configs also read `./data/runtime/auth.token`.

This is the source-checkout development topology and the one used by the
OpenClaw and MCP compose smoke coverage. It is not the default user install
path.

Compose-backed bot-surface smoke commands:

```bash
node integrations/openclaw/froglet/test/compose-smoke.mjs
node integrations/mcp/froglet/test/compose-smoke.mjs
```

## Single-Role Compose Files

- `compose.provider.yaml`
- `compose.runtime.yaml`

Examples:

```bash
docker compose -f compose.provider.yaml up --build
docker compose -f compose.runtime.yaml up --build
```

## Direct Image Builds

```bash
docker build --target provider -t froglet-provider:local .
docker build --target runtime -t froglet-runtime:local .
docker build --target dual -t froglet-dual:local .
docker build -f integrations/mcp/froglet/Dockerfile -t froglet-mcp:local .
```

## Published Images

The tagged release workflow publishes:

- `ghcr.io/armanas/froglet-provider:<version>`
- `ghcr.io/armanas/froglet-runtime:<version>`
- `ghcr.io/armanas/froglet-dual:<version>`
- `ghcr.io/armanas/froglet-mcp:<version>`

These tags are human-facing aliases. Successful bootstrap records and uses the
matching `@sha256:` references from the verified Release Bundle.

If the repository stays private, GitHub package visibility must still be set to
public before anonymous pulls work.

## Role Defaults

Provider image:

- public API on `:8080`
- no public runtime listener
- includes `python3` for published Python-backed services

Runtime image:

- runtime API on `:8081`
- no public provider listener

Dual image:

- provider API on `:8080`
- runtime API on `:8081`
- released no-service-manager Docker fallback used by agent bootstrap

Use `FROGLET_MARKETPLACE_URL` on runtime nodes to point them at an external
marketplace for discovery. A default public marketplace is available at
`https://marketplace.froglet.dev` and accepts self-registration for providers
that advertise a public HTTPS URL, a Tor v3 onion URL, or a claimed
`*.providers.froglet.dev` hostname.

## Isolated OCI workload execution

Froglet Node does not open a local Docker or Podman socket and does not spawn a
container-engine process for published OCI workloads. OCI execution is
disabled unless an authenticated isolated worker is configured:

```bash
export FROGLET_OCI_WORKER_URL=https://worker.internal.example/v1/execute
export FROGLET_OCI_WORKER_TOKEN_PATH=/run/secrets/froglet-oci-worker-token
```

The token path is preferred over `FROGLET_OCI_WORKER_TOKEN`; on Unix it must be
a regular, non-symlink file with mode `0600`. Plain HTTP is accepted only for a
literal loopback sidecar address.

The node sends only a digest-pinned image reference, input, bounded resource
limits, and the intersection of declared and granted logical capabilities.
Mount bindings and secret values never cross this seam; the worker resolves
logical handles inside its own trust boundary. Responses are byte-capped
before JSON parsing and must bind the exact request hash, image digest, and
granted-capability hash. Keep Docker/Podman/Kubernetes credentials and sockets
inside the isolated worker environment, never in the Froglet Node container.
